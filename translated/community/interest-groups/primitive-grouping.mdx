## 群组类型

**兴趣组**

## 使命陈述

原语分组兴趣组探索如何在协议所维护的扁平列表之外组织 MCP 原语（工具、资源、提示、任务），以及此类组织如何同时惠及 MCP 服务器和客户端。本群组记录来自客户端、服务器和网关的多样化需求，支持各种组织策略的参考扩展，并将建议输入 [SEP 流程](/community/sep-guidelines)，而非过早地选定单一的规范模式。

## 范围

### 范围内

- **需求收集**：记录用例和约束
- **模式探索**：测试并评估各种方法
- **概念验证**：维护一个共享的参考实现和实验发现仓库

### 范围外

- **批准规范变更**：本 IG 无权批准协议变更；建议经由 SEP 流程流转
- **实现强制**：本群组可以记录模式，但不能要求特定的客户端或服务器行为

### 相关群组

- **[工具标注 IG](/community/interest-groups/tool-annotations)** —— 基于标注的原语过滤和选择，与原语如何被组织和呈现相交叉
- **[Skills Over MCP 工作组](/community/working-groups/skills-over-mcp)** —— MCP 与 Skills 的相关工作正在评估能力如何被发现和组织，这与分组重叠
- **[Registry 工作组](/community/working-groups/registry)** —— 组织 MCP 服务器（超出本群组职责）在那里评估
- **[安全 IG](/community/interest-groups/security)** —— 按权限级别组织和披露原语是一项安全关切，在本群组范围之外

## 问题陈述

MCP 原语的扁平列表可能又长又难以处理，原因有若干。许多此类问题在本群组范围内，但有些不在。

**范围内**

- **上下文过载** —— 当加载到 LLM 的上下文中时，原语列表可能压垮模型，导致混淆和糟糕的选择
- **低效的操作** —— 上下文中的长列表消耗大量 token，从而增加处理成本和响应延迟
- **糟糕的开发者体验** —— 缺乏针对原语的组织工具，使它们更难管理和维护

**范围外**

- **为安全而组织** —— 基于客户端的权限级别来组织和向其披露原语是一个重要问题，但超出本群组职责
- **组织 MCP 服务器** —— MCP 注册表和 MCP-and-Skills 群组正在评估应如何组织不同的服务器以改善客户端体验

## 目标

1. **记录需求与经验** —— 记录实现这些扩展的不同客户端、服务器和网关的多样化需求。我们**不会**试图过早达成共识，而是旨在基于来自现实世界经验的反馈记录各种取舍。
2. **参考扩展** —— 许多可能的组织机制正在涌现，现在选定一个规范模式或许为时过早。不同的服务器正在实现相似的特性，但缺乏标准化限制了客户端有效利用它们的能力。本群组将支持各种组织策略的参考扩展，例如分组、工具搜索、code-mode。
3. **推广标准** —— 邀请大型 MCP 服务器和客户端的开发者及维护者提供反馈，以从定制实现迁移到标准化扩展。

## 组织策略

参见[各种方法](https://github.com/modelcontextprotocol/experimental-ext-grouping/blob/main/docs/approaches.md)，其中详细描述了每种策略，包括先前技艺、示例和讨论链接。

## IG 原则

1. **记录讨论** —— 本 IG 旨在记录各种取舍和讨论，而非规定某一特定实现。相比冗长的 Discord 话题，更倾向于在 IG 仓库上使用 GitHub Discussions。同步 IG 电话会议的会议纪要也会上传到 GitHub Discussions 以备日后参考。
2. **实验性扩展** —— 该仓库容纳针对不同方法的实验性扩展。扩展**应当（SHOULD）**至少支持 Python 和 TypeScript 实现，并包含 (1) 端到端可运行的演示和 (2) 关于他人如何与之集成的详细说明。
3. **来自部署的反馈** —— 本 IG 征集扩展用户的部署经验和反馈，以对特性开发和变更进行优先级排序。

## 生命周期

**当前状态：活跃探索**

### 毕业标准（IG → WG）

本 IG 在以下情况可以提议转为工作组：

- 就一种需要持续规范工作的方法出现明确共识
- 跨领域协调需要正式的权限委派
- 至少两位核心维护者担保 WG 的组建

### 退役标准

- 问题领域已解决（约定已确立、被其他 WG 吸收）
- 参与不足以维持势头
- 社区共识认为分组不属于 MCP 协议范围

## 成功标准

- **短期**：就需求和对现有方法的评估形成成文的共识
- **中期**：给出明确的建议（约定 vs. 协议扩展 vs. 两者兼有）
- **长期**：跨 MCP 服务器和客户端的可互操作分组约定
